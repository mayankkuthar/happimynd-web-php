# HR Auto API contract

**For:** whoever ports the HR Auto (Resume Extractor) backend to MySQL.

This is every HTTP endpoint the web app calls today, with the request, the response and the rules behind it. If the API keeps these paths and shapes, the front end needs no changes. The current implementation is the reference: `server/src/app.ts`, the routers in `server/src/http/routes/`, and `server/src/db/records.repo.ts` for the SQL behind them.

**Who calls what:** every call is in `frontend/src/api.ts`.

| Area           | Endpoints                                                                   |
| -------------- | --------------------------------------------------------------------------- |
| Sign-in        | `/api/login`, `/api/logout`, `/api/session`                                 |
| Metadata       | `/api/health`, `/api/schema`                                                |
| Resumes        | `/api/resumes/upload`, `/api/resumes`, `/api/resumes/:id`, `/api/resumes/:id/*` |
| Export and log | `/api/export`, `/api/logs`                                                  |
| Infrastructure | `/api/health/ready` (load balancer only; the web app never calls it)        |

**Which endpoints touch the database:** all of them except `/login`, `/logout`, `/session` and `/schema`. `/health` and `/health/ready` run `SELECT 1`.

---

## 1. Conventions

- **Base path:** `/api/...`. In production the browser calls the Vercel app's own origin, and `frontend/vercel.json` rewrites `/api/*` to the API. The browser sees one origin.
- **Path aliases:** the resume router is mounted twice. `/api/resumes/...` is what the web app calls; `/api/records/...` is the original path and behaves identically. `POST /api/upload` is the alias of `POST /api/resumes/upload`. Keep both.
- **Format:** JSON in and out, except upload (multipart), file preview (the file's bytes), export (`.xlsx`) and logs (plain text).
- **Errors** use FastAPI's envelope, because this API replaced a Python one:
  - A raised error: `{ "detail": "Human readable message" }` with its status. The front end shows `detail`.
  - A request that fails validation: **422** `{ "detail": [ { "loc": ["body", "fields"], "msg": "…", "type": "…" } ] }`.
  - Malformed JSON body: **422** `{ "detail": [ { "loc": ["body"], "msg": "Request body is not valid JSON.", "type": "json_invalid" } ] }`.
  - Unknown route: **404** `{ "detail": "Not Found" }`.
  - Anything unexpected: **500** `{ "detail": "Internal Server Error" }`. Never put a SQL error, connection string or path in a response.
- **Times:** stored in UTC. Responses carry `created_at` as **epoch seconds** (a float), and `elapsed_ms` as integer milliseconds.
- **IDs:** 12 lowercase hex characters, generated by the API at upload (`randomUUID()` without dashes, first 12).
- **Sources:** `linkedin`, `indeed`, `naukri`, `email`, `others`. One per dashboard tab. **Data is isolated per source**: every list, count, clear and export is filtered by it.
- **Departments:** `Business Development`, `Digital Marketing`, `Client Servicing`, `Psychology`, `Torchbearer`, `IT`, `HR & Finance`. Stored as this display label. `null` for resumes uploaded before departments existed.

### Validation of `source` and `department`

| Case                          | Response                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------- |
| Missing or empty              | **422** `{ "detail": [ { "loc": ["query" or "body", "source"], "msg": "Field required", "type": "missing" } ] }` |
| Present but not in the list   | **400** `"Unknown source 'x'. Expected one of: linkedin, indeed, naukri, email, others."` (department: same pattern) |

### CORS

`Access-Control-Allow-Origin` is echoed for origins in `CORS_ORIGINS` (comma-separated env var), with `Allow-Credentials: true`, methods `GET, HEAD, POST, PATCH, DELETE`, and `Content-Disposition` exposed so downloads keep their file name. With the Vercel rewrite, the browser never makes a cross-origin call; CORS only matters if the front end calls the API directly.

## 2. Sign-in

There's a single admin account, configured by env vars. No user table, nothing stored in the database.

| Variable                  | Contents                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `ADMIN_USERNAME`          | Compared in constant time                                                                       |
| `ADMIN_PASSWORD`          | Plain text in the env, compared in constant time. Both comparisons always run.                 |
| `SESSION_SECRET`          | HMAC key for the cookie. Unset → random per boot (everyone signed out on restart; breaks multi-instance). |
| `SESSION_TTL_HOURS`       | Default 12                                                                                      |
| `SESSION_COOKIE_SAMESITE` | `Lax` in production behind the Vercel rewrite                                                   |

**Session cookie** `hr_session`:

| Part       | Value                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------ |
| Value      | `<expiry ms epoch>.<signature>` (URL-encoded)                                              |
| Signature  | base64url of `HMAC-SHA256(SESSION_SECRET, "<expiry ms epoch>")`                            |
| Attributes | `Path=/; HttpOnly; SameSite=<Lax/None/Strict>; Max-Age=<TTL seconds>`, plus `Secure` in production or with `SameSite=None` |

Valid only if the signature verifies and the expiry is in the future.

**Gate:** every `/api/*` route except `/health`, `/health/ready`, `/login`, `/logout` and `/session` returns **401** `{ "detail": "Not authenticated" }` without a valid cookie. The web app treats any 401 as "session expired" and shows the login screen.

### `POST /api/login`

- **Body:** `{ username: string, password: string }` (both required strings, else 422).
- **Success:** `200 { "authenticated": true }` + `Set-Cookie`.
- **Wrong username or password:** `401 { "detail": "Incorrect username or password" }`. One message for both.

### `POST /api/logout`

Returns `200 { "authenticated": false }` and clears the cookie (same attributes, `Max-Age=0`).

### `GET /api/session`

Returns `200 { "authenticated": boolean }`. Never 401.

## 3. Metadata

### `GET /api/health`

**Always 200**, and `status` is always `"ok"`, even if the database is down. The web app reads this and renders a different screen on any non-OK response, so a database blip must not change it.

```json
{
  "status": "ok",
  "ai_enabled": true,
  "model": "openai.gpt-oss-120b-1:0",
  "database": "ok",
  "storage": "gcs",
  "processor": { "running": true, "active": 2, "concurrency": 2 }
}
```

- `model` is `null` when AI is off.
- `database`: `"ok"` | `"unreachable"` | `"not configured"` (from `SELECT 1`).
- `status`, `ai_enabled` and `model` are the contract; the rest is additive diagnostics.

### `GET /api/health/ready`

For the load balancer. **200** `{ "status": "ready", database, storage, processor }` when `SELECT 1` succeeds, otherwise **503** with `"status": "not ready"`. Use this as the AWS health check.

### `GET /api/schema`

Field metadata, so the front end hardcodes no column list. Doesn't touch the database.

```json
{
  "labels": { "file_name": "Resume File Name", "candidate_name": "Candidate Name", "…": "…" },
  "order": ["file_name", "candidate_name", "…"],
  "default_visible": ["file_name", "candidate_name", "email", "…"],
  "list_fields": ["certification_names", "project_names", "technical_skills", "…"]
}
```

56 fields. Source of truth: `server/src/domain/schema.ts`. `list_fields` is sorted alphabetically.

## 4. Resumes

### Shared objects

```ts
type Status = "queued" | "processing" | "done" | "error";
type Confidence = "high" | "medium" | "low" | "none";
type FieldValue = string | string[] | null;     // list fields are string[]

interface RecordSummary {                       // toSummary() in server/src/domain/records.ts
  id: string;
  file_name: string;
  has_file: boolean;                            // storage_key IS NOT NULL
  size_bytes: number;
  content_type: string;                         // e.g. "application/pdf", "image/png"
  source: Source;
  department: Department | null;
  status: Status;
  viewed: boolean;                              // MUST be a JSON boolean (TINYINT → Boolean())
  fields: Record<string, FieldValue>;           // the `fields` JSON column, as stored
  confidence: Record<string, Confidence>;       // the `confidence` JSON column, as stored
  error: string | null;
  used_ocr: boolean;                            // MUST be a JSON boolean
  page_count: number;
  ai_status: "ok" | "failed" | "disabled" | "skipped";
  duplicate_of: string | null;
  log: string[];                                // the `log` JSON column
  created_at: number;                           // epoch SECONDS, from created_at (UTC)
  elapsed_ms: number | null;                    // finished_at − created_at, null until finished
}

interface Stats { queued: number; processing: number; done: number; error: number; total: number }
```

`text_content` is **never** in a list response. List queries select `'' AS text_content`, because a poll of 500 rows would otherwise ship megabytes of resume text.

### `POST /api/resumes/upload` (alias `POST /api/upload`)

**Multipart:** `files` (one or more), `source`, `department`. Both text fields are validated before anything is stored; a bad one rejects the whole request.

**Per file, in order:**

1. Name: decoded from latin1 to UTF-8, path stripped, control characters and leading dots removed, trimmed, cut to 255 characters; `"unnamed"` if empty.
2. Rejections (the file is skipped, the rest of the batch continues):
   | Check                                          | `reason`                                   |
   | ---------------------------------------------- | ------------------------------------------ |
   | 0 bytes                                        | `Empty file`                               |
   | Over `MAX_FILE_BYTES` (25 MB)                  | `Larger than 25 MB`                        |
   | Extension not in `ALLOWED_UPLOAD_EXTENSIONS`   | `Unsupported file type (.xyz)` / `Unsupported file type (no extension)` |
   | Object storage write failed                    | `Could not be stored — please retry`       |
   | Database insert failed (object is then deleted) | `Could not be saved — please retry`       |
3. ID: 12 hex characters. Storage key: `resumes/<source>/<id>.<ext>` (`ext` sanitised, else `bin`).
4. Content type sniffed from the bytes, not taken from the browser.
5. **Insert** (`repo.insert`), in one transaction:
   - Look for the oldest row with the same `source` and `checksum` (SHA-256 hex of the bytes) and `duplicate_of IS NULL`, `FOR UPDATE`.
   - Insert with `status = 'queued'`, `duplicate_of` = that row's id (or `NULL`), and `log = ["Duplicate of <original file_name> (identical file contents)."]` when it's a duplicate, else `[]`.
   - Duplicates are **flagged, not rejected**.

**Response:** `200 { accepted: RecordSummary[], rejected: [{ file_name, reason }], stats: Stats }` (stats for this source). Extraction happens afterwards on the background queue; the client polls the list endpoint.

Multer-level failures return 400: too many files → `"Too many files in a single upload."`; a file over 4 × `MAX_FILE_BYTES` → `"One of the files exceeds the maximum upload size."`.

### `GET /api/resumes?source=<source>`

The polling endpoint. `200 { records: RecordSummary[], stats: Stats }`, both for that source only, records ordered by `created_at` ascending.

### `DELETE /api/resumes?source=<source>`

Deletes every record of that source, then their stored files (rows first: an orphaned file is recoverable, a row pointing at a deleted file breaks the preview). `200 { deleted: <number of files>, stats: Stats }` (this source, now all zero).

### `GET /api/resumes/:id`

`200 { ...RecordSummary, text: string, candidate: Candidate }`. `text` is the full `text_content`. `404 "Record not found"`.

```ts
interface Candidate {            // toCandidate() in server/src/domain/candidate.ts — derived from `fields`, nothing stored
  id: string;
  name: string | null; email: string | null; phone: string | null; location: string | null;
  education: string[]; experience: string[]; skills: string[]; projects: string[]; certifications: string[];
  linkedin: string | null; github: string | null; portfolio: string | null;
  yearsOfExperience: number | null;
}
```

### `GET` / `HEAD /api/resumes/:id/file`

Streams the original file from object storage for in-browser preview.

- Headers: `Content-Type` = the stored `content_type`; `Content-Disposition: inline; filename="<ascii-scrubbed>"; filename*=UTF-8''<encoded>`; `Cache-Control: private, max-age=3600`; `Content-Security-Policy: sandbox; default-src 'none'`.
- `HEAD` sends `Content-Length` and no body.
- `404 "File not found"` when the record has no `storage_key` or the object is gone.

### `PATCH /api/resumes/:id`

Manual edit from the results table.

- **Body:** `{ fields: { <field>: string | string[] | null, … } }`. At least one key; every key must be one of the 56 field names (`Unknown field 'x'` → 422). A non-list field can't take an array (`Field 'x' is not a list` → 422).
- **Normalising:** list fields accept an array or `;`-separated text and become a trimmed array with blanks removed (`null` → `[]`). Other fields are trimmed; empty becomes `null`.
- **Write:** merge the edits into `fields` **keeping `null` values** (see MIGRATION_GUIDE §5: use `JSON_SET`, not `JSON_MERGE_PATCH`), and set `confidence[<field>] = "high"` for each edited key. A human checked it.
- **Response:** `200 RecordSummary`. `404 "Record not found"`.

### `PATCH /api/resumes/:id/viewed`

- **Body:** `{ viewed: boolean }`.
- `200 RecordSummary`, `404 "Record not found"`.

### `POST /api/resumes/:id/reprocess`

Puts the record back on the queue: `status = 'queued'`, `log = []`, `error = NULL`, **`created_at = now`**, `finished_at = NULL`, `claimed_at = NULL`, `attempts = 0`. Resetting `created_at` moves the row to the bottom of the table; that's intended. Returns immediately (`200 RecordSummary`); the client polls. `404 "Record not found"`.

### `DELETE /api/resumes/:id`

Deletes the row, then its stored file. `200 { deleted: "<id>", stats: Stats }`, where **`stats` counts every source, not this record's source**. It's the one place that does, and clients were written against it. `404 "Record not found"`. Other rows that pointed at it through `duplicate_of` get `NULL` (foreign key `ON DELETE SET NULL`).

## 5. Export and log

### `POST /api/export`

- **Body:** `{ source: Source, ids?: string[] | null, highlight_low_confidence?: boolean }` (default `true`).
- Selects `status = 'done'` records of that source, optionally only those `ids`, ordered by `created_at`. **An empty `ids` array selects nothing** (Postgres `= ANY('{}')`); in MySQL, return early instead of sending `IN ()`.
- None found: `400 "No completed records to export"`.
- Marks them all `viewed = true` **before** building the sheet, so its "Reviewed" column agrees with the table. If that update fails, the export still goes out with the old values.
- **Response:** the `.xlsx` bytes, `Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `Content-Disposition: attachment; filename="candidates_YYYYMMDD_HHMMSS.xlsx"` (server local time).
- A copy is saved to storage under `exports/<YYYY-MM>/<file name>` in the background. A failure there never affects the download.

### `GET /api/logs?source=<source>`

Plain-text extraction log for every record of the source, in `created_at` order. `Content-Disposition: attachment; filename="extraction_log.txt"`.

```
=== resume.pdf [done] ===
  id: a1b2c3d4e5f6  pages: 2  ocr: False
  ERROR: <error, only if set>
  - <each log entry>
  low confidence: email, phone          <- only if any field is "low", sorted
<blank line>
```

`True`/`False` are capitalised (Python style) on purpose. With no records the body is `No records processed yet.\n`.

## 6. Background processing (not HTTP, but it writes the same table)

Every API instance runs this loop (`server/src/services/processor.ts`); it is the main writer of `records` after upload.

| Step       | What it does                                                                                       | SQL (`records.repo.ts`) |
| ---------- | -------------------------------------------------------------------------------------------------- | ----------------------- |
| Claim      | Oldest `queued` row → `processing`, `claimed_at = now`, `attempts + 1`. Up to `EXTRACT_CONCURRENCY` in flight per instance. Polls every 1 s when idle. | `claimNext` — `FOR UPDATE SKIP LOCKED` (MIGRATION_GUIDE §5.1) |
| Success    | `status = 'done'`, replace `fields`, `confidence`, `text_content`; **append** to `log`; set `used_ocr`, `page_count`, `ai_status`; `error = NULL`, `finished_at = now`, `claimed_at = NULL` | `markDone` |
| Failure    | `status = 'error'`, `error = <message>`, append `"Processing failed: <message>"` to `log`, `finished_at = now`, `claimed_at = NULL` | `markFailed` |
| Reaper (every 60 s, and at boot) | Rows `processing` with `claimed_at` older than `STUCK_JOB_TIMEOUT_MS` (10 min): if `attempts >= MAX_PROCESS_ATTEMPTS` (3) → `error` with `"Processing timed out and exceeded the retry limit."`; otherwise back to `queued` | `reapStuck` — two `UPDATE`s, in that order |

On shutdown (SIGTERM) the loop stops claiming and lets in-flight rows finish, so their results are saved.

## 7. Caching and timing

| Data                         | Cached where                       | Duration                        |
| ---------------------------- | ---------------------------------- | ------------------------------- |
| Record list                  | Not cached; the web app polls it   | Every 1.2 s (`POLL_INTERVAL_MS` in `ExtractorScreen.tsx`) |
| Original file preview        | Browser (`private, max-age=3600`)  | 1 hour; a stored file never changes |
| `/api/schema`                | Not cached by the server           | Read once per page load         |
| Everything else              | Not cached                         |                                 |

An upload shows up as `queued` immediately and becomes `done` once a worker gets to it, typically seconds per resume, longer with OCR or under Bedrock throttling.
